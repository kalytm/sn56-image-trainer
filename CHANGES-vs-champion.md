| D1 | `trainer/godtrainer/selection.py` (new); `engine.py` (`holdout_score`, `evaluate_candidates`, `_select`, delta-average, member/soup acceptance via `Trainer._better`, `_base_eval`, `HoldoutAborted`); `train.py` (`--select-rule`, `--select-k`, `--base-eval-frac`, validation); `scripts/image_trainer.py` (`COMMON`, Ideogram extras) | Holdout uses 4 seeded noises per band (the champion used 1, Flux 2; the official evaluator uses 16, so 4 is a variance-reduction compromise, not a match). Every candidate keeps its paired per-image vector under a member-qualified tag (`m1:ema@300`), so members never share a key. With ≥3 holdout images a candidate replaces the best only if its paired gain exceeds k·SE across images (k=1, a heuristic); otherwise a smoother/later state (deltaavg > ema > raw > base) wins only if its per-image mean is not worse. With <3 images the champion's lower-mean rule applies. Paired mode always scores arithmetic means: `train.py` rejects other `--select-metric` values with it, and Ideogram's p75 was dropped. Deadline guard: the identity fallback is saved before any scoring. Every holdout evaluation runs against a cutoff (the task deadline minus the save reserve, and inside a member also the member's budget): it refuses to start when the cutoff has passed or the last measured cost cannot fit, projects the remaining cost before every forward batch, and discards a result that completes late. An aborted candidate scores NaN (never replaces), later candidates at that point are skipped, and the projected cost becomes the new estimate. The base evaluation aims for ≤15% of the remaining budget by reducing the noise count (fixed for the rest of the run, estimate rescaled); at one noise it may use the whole scoring budget, so 15% is not a hard cap. `--select-rule min` reproduces the champion's selection. | implemented; codex 4c009d0 findings addressed; CPU tests pass; **no GPU A/B yet**. `retrain_all` (inherited, disabled) is outside the paired rule. |

| D7 | `engine.py` (`_forward_backward`, `ckpt_full`) | Memory fallback. The champion's Ideogram4 recipe turns gradient checkpointing off (`--no-ckpt`) for speed, which runs at the 80 GB limit: in B2 (H100 80 GB) dev task 04ac2174 (latents 47×64) trained, but ea66240a (48×64, 768×1024 images) ran out of memory at step 1 for the champion and for ours, and both produced only the untrained identity LoRA. Now, when a training step runs out of GPU memory while some blocks are not checkpointed, the step's partial gradients are dropped, every transformer block is checkpointed (stride 1) and the step is retried once; a second out-of-memory, or one with all blocks already checkpointed, is raised as before. The retry starts only if 1.5× the larger of the failed attempt and the current step estimate, plus the reserve the loop keeps after a step (D3 tail or the time schedule's evaluation reserve; none for fixed-step retraining), fits the member cutoff; otherwise the member ends on its best state with no update. After a retry the D3 schedule drops its earlier (faster-mode) step samples, takes the iteration's preparation plus the retried step (excluding the failed attempt and recovery) as the new estimate and replans at once (the horizon still only shrinks); the time schedule's step estimate is reset. Checkpointing stays on for later members. Tasks that fit keep the fast path unchanged. The trigger is a runtime memory error, never task identity. Recorded in `summary.json` as `memory_fallback`. | implemented; codex 432f455 and 464af3a findings addressed; CPU tests pass (control flow with a stand-in exception, incl. the real `train_member` loop); GPU check passed in B2 (ideogram4 ea66240a, H100 80 GB): out of memory at step 2, 34 blocks checkpointed, retried and trained at ~2.1 s/step (716 steps); test loss 0.43418 vs the champion's 0.48045 (the champion produced only the untrained LoRA), -9.6%.
